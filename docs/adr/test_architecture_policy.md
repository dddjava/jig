# テストは利用者が観測する契約で組み立てる

## 状況 (Context)

JIG は Java・クラスファイル・設定ファイルを入力に、HTML・データ JS・JSON を出力し、CLI と Gradle プラグインから実行されます。テストは、利用者が観測する振る舞い、公開する形式、対応する実行環境を保証する必要があります。

JIG の入力はクラスファイルであり、Javadoc など一部の情報には対応するソースも必要です。代表的な入力を複数モジュールで共有し、解析対象の Java バージョンを再現可能に検証する必要があります。

高速な原因特定と、実際の配布物・生成サイトに対する信頼性は両立させます。すべての検証を通常の `build` に含めると開発時のフィードバックが遅くなるため、隔離度に応じて実行入口を分けます。

## 決定 (Decision)

### 契約

すべてのテストを、次の契約のいずれかに結び付けます。

| 契約 | 利用者に起きること | 主な検証手段 |
| --- | --- | --- |
| 解析契約 | 入力からモデルを誤認識する | Unit、Component、代表プロジェクト |
| 出力契約 | HTML・データ JS・JSON・アセットが壊れる、または内容が変わる | Contract、構造検証、決定性検証 |
| 起動契約 | CLI または Gradle タスクから実行できない | CLI E2E、Gradle TestKit |
| 互換性契約 | サポートする JDK・OS・Gradle・ブラウザ・クラスファイルで動かない | 互換性マトリクス、複数バージョンの fixture |

実行環境と解析対象クラスファイルの対応範囲は、それぞれのバージョンサポート ADR に従います。

### テスト階層

同じ振る舞いを複数階層で繰り返しません。下位層は原因特定、上位層は結線と利用者体験を保証します。

| 階層 | 対象 | 許可する依存・I/O | 実行頻度 |
| --- | --- | --- | --- |
| Unit | 値オブジェクト、判定、変換、ドメイン規則、画面資産の純粋関数 | 実ファイル、ネットワーク、Gradle、ブラウザを使わない | 全 PR |
| Component | 一つのアダプターまたはアプリケーション・ユースケース | テンポラリファイル、埋め込みパーサー、テスト用実装まで | 全 PR |
| Contract | JIG が生成・消費する公開形式 | バージョン管理された fixture | 全 PR |
| E2E | CLI、Gradle プラグイン、生成済みサイト | 実プロセスと隔離した代表プロジェクト | 全 PR |
| Compatibility | サポート対象の組合せ | 実 JDK/OS/Gradle/ブラウザ、複数バージョンの fixture | 対象ごとの CI |

決定性は Contract の検証項目とします。性能とメモリ消費には自動の合否判定を設けず、必要時に計測します。

### fixture と入力

- 代表プロジェクトはテスト専用モジュール `jig-test-fixtures` に置き、本番成果物の依存グラフへ入れません。
- fixture API がクラス出力ディレクトリとソースディレクトリの対を返し、利用側のテストはビルドレイアウトを組み立てません。
- 解析対象の Java バージョンは、同一ソースを `--release` ごとにコンパイルして検証します。
- ファイルシステム経由の入力だけを必要とする小さな検証は、対象テストの `ut` パッケージに置いた fixture を利用します。実行時クラスパスから読むリソースは `jig-core` のテストソース・リソースに置きます。
- 実ライブラリを読む規則は最小の公開 API を模した fixture を優先し、実ライブラリとの結線確認は Compatibility または E2E に一件置きます。アノテーションの所在自体が契約である場合は実ライブラリを使用します。
- 期待値を固定する入力に JIG 自身の解析結果を使いません。自己解析は大きな入力に対する挙動確認に限ります。

### 実行入口

- `check` は Unit、Component、Contract を実行します。
- `qualityCheck` は `check`、E2E、JaCoCo レポートを束ねます。`build` から E2E へ依存を追加しません。
- Gradle TestKit は PR で全サポート対象を実行するため、専用ソースセットを増やさず `src/test` に置きます。
- JavaScript の Unit/Component と、生成サイトを読む Contract は Node.js のテストとして実行します。

| 入口 | 内容 |
| --- | --- |
| `./gradlew test` | 全モジュールの Unit/Component と Gradle TestKit |
| `./gradlew contractTest` | Java の公開形式 Contract |
| `./gradlew e2eTest` | CLI E2E |
| `./gradlew qualityCheck` | `check`・E2E・カバレッジレポート |
| `npm run test` | Web の Unit/Component |
| `npm run test:contract` | Java Contract と生成サイトを読む Web Contract |
| `npm run test:full` | 開発中の標準入口 |
| `npm run test:pr` | PR と同じ全検証 |

### 生成物と観測点

- JSON は構造、HTML は DOM の必須構造・リンク・アクセシビリティ属性で検証します。
- スナップショットは構造で表せない図や文章に限定し、通常のテスト実行中には更新しません。
- 同一入力に対する出力の一致を検証し、時刻・絶対パス・ランダム値・OS の区切り文字は成果物に残さないか、比較前に正規化します。
- テストの都合で本番コードの可視性を上げません。観測点は公開契約または専用に設計した境界に置きます。
- `learning` は品質保証の実行対象に含めず、仕様を固定するときに適切な階層へ移します。

### 追加時の規則

1. 追加するテストでは、壊れたときに利用者へ起きることを先に言語化し、契約と階層を選びます。
2. Unit はネットワークと実プロセスを起動しません。実プロセスを起動できるのは E2E だけです。
3. 実ネットワーク、現在時刻、共有ディレクトリ、テスト実行順序に依存しません。
4. カバレッジは収集しますが、しきい値による合否判定を置きません。公開シナリオの網羅、失敗の再現性、テスト時間と併せて判断します。
5. 本番コードのパッケージ間依存、性能、変異解析には自動の合否判定を設けません。

## 結果 (Consequences)

- テストの失敗を、利用者に起きる不具合として読めるようになります。
- fixture と互換性の検証を共有・再現可能に保てます。
- 日常の開発では高速な検証を使い、PR とリリースでは公開契約と配布経路まで確認できます。
- モジュール・ソースセット・実行入口が増えるため、テスト追加時には契約と階層を明示する判断が必要です。
